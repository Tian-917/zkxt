# 证书域压测报告（P4）

> 环境：本机 5 个服务 + VM 上 MySQL/Redis/RabbitMQ，Windows，单机
> 工具：[tools/load_cert.py](../tools/load_cert.py)（Python 线程池并发，非 JMeter）
> 时间：2026-10

## 1. 结果

| 场景 | 请求数 | 并发 | 成功率 | QPS | P50 | P95 | P99 | MAX |
|---|---|---|---|---|---|---|---|---|
| **A 幂等**：同一场考试 500 次发证 | 500 | 100 | 500/500 | 105 | 201ms | 3837ms | **3965ms** | 4045ms |
| **B 唯一**：300 个不同考试并发发证 | 300 | 100 | 300/300 | 283 | 300ms | 432ms | **508ms** | 529ms |

**正确性校验（数据库）**

| 校验项 | 期望 | 实际 |
|---|---|---|
| `exam_id=900001` 的证书行数 | 1 | **1** |
| A 组返回的不同证书编号数 | 1 | **1** |
| B 组落库行数 | 300 | **300** |
| 全表证书数 / 编号去重后 | 相等 | **306 / 306** |

## 2. 关键发现：P99 差 8 倍，原因是"热点行"

同样是 100 并发，A 组 P99 3965ms，B 组只有 508ms。差别只有一个：**A 组的 500 个请求抢同一个唯一键**。

链路拆开看：

```
500 个请求都走「先查 -> 没查到 -> 尝试 insert」
    ↓
第 1 个成功，其余 499 个 insert 撞 uk(user_id, exam_id)
    ↓
每个失败插入都要等唯一索引的行锁 + 抛 DuplicateKeyException + 回查
    ↓
锁等待排队 -> 尾部延迟被放大到 4 秒
```

这是**幂等正确但有性能代价**的典型形态：用唯一索引兜底保证了"只发一张证"，代价是高并发同键时行锁排队。

## 3. 如果继续优化，方向是什么

| 方案 | 做法 | 代价 |
|---|---|---|
| Redis 前置去重 | 进 DB 前 `SETNX cert:issue:{userId}:{examId}`，抢不到的直接走查询 | 要处理"抢到锁但证还没落库"的空窗，需要短轮询 |
| 结果缓存 | `examId -> certNo` 缓存，重复请求直接返回 | 缓存一致性 |
| 异步化 | 发证请求先返回"受理中"，证书异步生成 | 前端要改交互 |

**这次没做**：正确性优先，先把「并发只发一张」焊死。优化方向写在这里，面试时讲"我发现了什么、为什么这次不改"比硬堆一个实现更真实。

## 4. 复现方式

```bash
# 确保 cert-service(8091) 在跑
python tools/load_cert.py
```

脚本会打两组流量并直接查库校验，输出上表的全部数字。
