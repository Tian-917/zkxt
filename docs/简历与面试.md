## 一、简历写法

### 项目一：职考云 · 职业技能考证平台（个人项目）

**技术栈**：Java 11 / Spring Boot 2.7 / Spring Cloud Alibaba / Nacos / MySQL / Redis / RabbitMQ / Elasticsearch / MongoDB / XXL-Job

- 独立完成 15 个微服务（网关、鉴权、用户、课包、学习、考试、**证书**、交易、支付、优惠券、消息、检索、数据看板等）与 2 个公共模块，覆盖「学 → 练 → 考 → 证」完整闭环；
- 设计并实现证书域：资格判定（学时 + 成绩双达标）、证书编号（Redis 号段 + 唯一索引兜底）、公开验真、到期复证与失败补偿；**500 并发同一场考试只产生 1 张证**，300 个不同考试并发产出 300 个唯一编号，P99 508ms；
- 打通"考试通过自动发证"的最终一致链路（考试服务 → MQ → 证书域，失败落补偿表由 XXL-Job 重放），发证失败不影响交卷；
- 实现错题本：一题一条 + `ON DUPLICATE KEY UPDATE` 累加错误次数，重练答对自动置为已掌握，支持按考点聚合复盘。

### 项目二（可选，同一项目换角度）：微服务基础设施实践

- 基于 Nacos 配置中心管理 8 份共享配置，网关统一 JWT 鉴权与 Knife4j 文档聚合；
- 用 Elasticsearch 实现课包检索，课程上架通过 MQ 触发索引重建；
- 定位并修复跨服务事务失效问题（`@GlobalTransactional` 用在同类自调用方法上，AOP 不生效），改为本地消息表 + 补偿的最终一致方案。

## 二、面试 5 问 + 答题要点

### Q1：一个人为什么做微服务？拆分依据是什么？

**先承认**："这是我按生产架构练手的项目，不是真实业务驱动的。"

**再给判据**：
- 数据独立（各自库，不跨库 join）
- 变更频率不同（课包内容 vs 交易）
- 扩容需求不同（检索/考试是读多写少，交易是写多）
- 团队边界（虽然是模拟的）

**主动反思**（加分项）："15 个服务偏多，如果重来我会把 media/message/remark 合成 3~4 个服务，拆分粒度过细反而增加了联调成本。"

### Q2：分布式事务怎么保证？

**分场景答，不要一句"用 Seata"**：
- 主链路（考试通过 → 发证）：**最终一致**。考试服务发 MQ，证书域消费；失败落 `cert_task`，XXL-Job 补偿重放。发证失败**不回滚交卷**，因为交卷是用户已完成的事实。
- 强一致场景（如扣库存）：才考虑 Seata AT，代价是全局锁。
- **接一个真实发现**："项目里有个 `@GlobalTransactional` 加在同类自调用方法上，AOP 根本不生效，等于装饰品——这种'加了不等于生效'最坑。"

### Q3：证书编号为什么要 Redis 号段 + 唯一索引双重保证？

- Redis `INCR` 保证高并发下不重号（原子操作）
- 但 Redis 重启/回档后序号会回退 → 可能重号
- 所以 DB 再放 `uk(cert_no)`，冲突换号重试（最多 3 次）
- 不用 UUID：证书要给人看、要口播、要按年归档
- 不用数据库自增：多实例下不连续、暴露发证量

### Q4：消息重复/丢失怎么办？消费幂等怎么做的？

- 丢失：发送方确认 + 消费方手动 ack（项目用 Spring AMQP 的自动 ack + 失败重试），关键事件落本地消息表
- 重复：消费端幂等。证书域靠 `uk(user_id, exam_id)`，重复消息最多再查一次，不会发两张证
- 兜底：每日对账（考试通过名单 vs 已发证名单，差集补发）——设计里有，当前用 XXL-Job 补偿代替

### Q5：你踩过最深的坑？

**用 `docs/排查故事.md` 里的故事 3（P99 从 508ms 涨到 4 秒）**，因为它是自己测出来的、有数据：
> 500 个请求同一场考试并发发证，P99 3965ms；换 300 个不同考试，P99 只有 508ms。定位到唯一索引热点行：499 个请求都在等同一行的锁。功能没错，是幂等的代价。优化方向是 Redis SETNX 前置去重，但要处理"抢到锁、证还没落库"的空窗，所以我这次选择先保证正确性。

比"踩了 NPE 之类的坑"高一个层次：**发现问题 → 量化 → 定位 → 权衡是否修**。
